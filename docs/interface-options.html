Consuming App ↔ QuickBooks Service — Interface Options

Four ways the consuming web app could talk to QuickBooks. Pick by tradeoff, not by default.
Draft · 2026-05-21 · quickbooks-cli / cloud_functions

Option A — Web app calls QuickBooks directly

No service in between. The web app's backend implements its own OAuth + QBO REST client. qb CLI stays a separate ops tool.

↗ Pros

  • Simplest topology — one service less to deploy, monitor, and pay for.
  • No new auth surface; OAuth callback hits the web app directly.
  • No data-staleness questions — every read goes to the source of truth.
  • Easy to reason about: web app failures = QBO failures, not "is my sync service down?"

↘ Cons

  • Duplicates the OAuth + token refresh + rate-limit logic that already lives in qb/.
  • Every page load that needs Customers/Products hits QBO live → slower UX, burns rate limit (500/min/realm).
  • Phase 1 "daily sync" in the diagram has no natural home — would need to be a cron inside the web app.
  • If you later build a second consumer (mobile app, Slack bot, MCP server), each one re-implements QBO plumbing.
Fits when: you want to ship the smallest possible thing fast, accept the duplicated auth code, and don't expect a second QBO consumer. Worst fit if the Phase 1 daily sync + the My Jobs view both need cached customer/product lookups — caching pressure pushes you toward B or C anyway.

Option B — qb service as a thin stateless REST proxy

qb runs as a small HTTP service in front of QBO. No database of its own. Owns auth, refresh, rate-limiting, retries. Web app's DB is still the source of cached data.

↗ Pros

  • One place owns QBO auth, refresh, 429 retry, sparse-update quirks. Reuse for any future consumer.
  • qb stays small and stateless — easy to deploy as a single Cloud Function or Cloud Run service.
  • No new sync state to reason about; web app keeps full ownership of when/what it caches.
  • Centralized place to log every QBO call — debugging line-item mismatches becomes one log query.

↘ Cons

  • Adds a hop. Network failures between web app and qb are now a thing you handle.
  • Sync orchestration (Phase 1) still lives in the web app — qb is just the transport.
  • Two services to deploy. Mostly fine, but it is +1 thing.
  • Auth between web app and qb needs design (shared secret? IAM identity?).
Fits when: you want clean separation of concerns without the complexity of a sync service. The qb service becomes "the QBO adapter," nothing more. Probably the right default for this project — close to your gut instinct but skips the DB ownership question.

Option C — qb as a stateful sync service (your proposal)

qb owns its own DB. Pulls QBO → its DB on a schedule, exposes /sync, /invoice, /customers, etc. Web app reads from qb's REST and uses its own DB only for app-specific data (Jobs, Samples, Orders).

↗ Pros

  • Web app pages render from local cache → fast, predictable latency, no QBO rate-limit pressure on UX.
  • /sync is a real, named operation — easy to schedule, retry, observe, and debug.
  • QBO outages become read-only degradations, not full app failures.
  • Natural home for derived/joined data (e.g., per-client P&L already lives here).
  • Future MCP server, mobile app, or BI tool can all read the same cache.

↘ Cons

  • Two databases. "Is the customer I just created in QBO visible in qb's cache yet?" is now a question you answer constantly.
  • Writes need a story: write-through to QBO + immediate cache update, or write to QBO and wait for next sync? (First is almost always what you want, but it's design work.)
  • Schema migrations on qb's DB now require coordination — it's an integration contract.
  • More moving parts: scheduler, two DBs, two services. More to monitor.
  • Risk of qb growing into a second app — keep its scope ruthlessly narrow.
Fits when: the web app's read patterns are heavy enough that hitting QBO live is painful (latency, rate limit, or both), and you accept the operational cost of running a cache. Reach for this if Option B starts showing strain — don't start here.

Option D — Event-driven via QBO Webhooks + Pub/Sub

QBO pushes change notifications to qb via webhooks. qb fetches the changed entity and publishes to Pub/Sub. Web app subscribes. Writes still go through qb (or web → QBO directly). No polling.

↗ Pros

  • Near-real-time updates without polling — Vicky edits a customer in QBO, it shows up in the web app in seconds.
  • No daily-batch staleness window. Phase 1 "daily sync" disappears as a concept.
  • Naturally extensible — adding a Slack notifier or analytics consumer is just another subscriber.
  • Pub/Sub gives you replay + dead-letter for free, which is useful when QBO bursts notifications.

↘ Cons

  • Significant complexity bump. Webhooks need a public HTTPS endpoint, HMAC verification, idempotency, deduplication, ordering caveats.
  • QBO webhooks only tell you "Customer 42 changed" — you still have to fetch the entity. So the proxy/sync code from B or C is still required underneath this.
  • Local dev needs ngrok or similar to receive webhooks. Adds friction.
  • Overkill for a two-company lab with low transaction volume. Real-time is rarely the actual requirement.
  • Writes still need a path — webhooks are read-side only.
Fits when: staleness matters in seconds, not hours, and you have multiple consumers of QBO change events. For a daily-batch lab workflow with one consumer (the web app), this is almost certainly over-engineered — but worth knowing as the natural extension if you ever outgrow C.
Recommendation lean: start with Option B (thin REST proxy). It centralizes QBO knowledge in one place without committing you to a second database. Promote to C only if the web app starts showing read-latency or rate-limit pain. D is the long-term extension if real-time becomes a real requirement, not a wished-for one.
