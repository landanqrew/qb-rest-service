Codebase Readout · single realm · Python 3.13

A thin, stateless door between the Lab Intake app and QuickBooks Online.

Every request hits QBO live — the service owns Intuit OAuth, token rotation, rate-limit handling, and QBO's request/response quirks, and holds no business data of its own. One image, deployed as three Cloud Run services.

FastAPI · synchronous 19 routes 3 resources: customers · items · invoices token store: Secret Manager / file deploy: Cloud Run ×3

00 What it is

Forked from quickbooks-cli. The design contract (docs/qb-service-scope.md) is deliberately narrow: no business logic, no database, no caching, one QBO realm. It exists so the web app never sees an Intuit token or the client secret.

Owns
  • Intuit OAuth 2.0 handshake & browser bootstrap
  • Refresh-token rotation → Secret Manager versions
  • Rate limiting (local token bucket + 429 retry)
  • QBO fault-code → HTTP status translation
  • A stable, versioned /v1 REST surface
Explicitly not
  • No invoice numbering / test-code mapping — web app's job
  • No database, no cache — every read hits QBO
  • No CLI features (payments, estimates, P&L)
  • No webhooks, no multi-tenant shape

01 Request lifecycle

A request threads through two middleware layers, a rate-limit gate, and token management before a single outbound QBO call. Sync handlers run in FastAPI's threadpool — one inbound request maps to one outbound call.

retry logic

401 → refresh token, swap bearer, retry once. 429 → sleep Retry-After (default 5s), retry once; a second 429 raises RateLimitError. The local token bucket fails fast at ~480/min before hitting Intuit's 500/min ceiling.

02 HTTP surface

Data routes are versioned under /v1 and toggled by ENABLE_DATA_ROUTES. Admin OAuth routes are unversioned (the callback path is registered byte-for-byte in the Intuit console) and toggled by ENABLE_ADMIN_ROUTES. Writes are read-then-write against QBO's SyncToken optimistic concurrency.

04 Auth & token model

Two independent concerns: who may call the service (Cloud Run IAM + admin gate), and how the service talks to QBO (OAuth with rotating refresh tokens).

Caller → service

Cloud Run runs --no-allow-unauthenticated; GCP verifies the Google ID token at the edge before code runs.

  • AdminGateMiddleware — email-allowlist on /admin/*.
  • require_launch_authorization — HMAC launch token so a browser button can start OAuth without an identity token.

Service → QBO

Access token cached in-memory; refreshed when expired (60s buffer). Store is pluggable via TokenStore.

  • FileTokenStore — dev, JSON on disk, mode 600.
  • SecretManagerTokenStore — prod, new secret version per save, tombstone on clear.
critical

Refresh tokens rotate on every refresh. The new value must be persisted or the next cold start dies. A process-wide refresh_lock serializes refreshes (double-checked re-read under lock) so two threads can't invalidate each other's rotated token. A failed save() raises loudly — Intuit has already rotated by then.

07 Adding a feature — where it plugs in

The architecture is uniform, so a new read/write resource (say /v1/vendors or /v1/payments) is largely mechanical. Follow the existing resource modules; the interesting decisions are QBO-shaped, not framework-shaped.

Add the router module

Create routes/<resource>.py mirroring customers.py (read-only) or items.py (CRUD). Reuse _common.list_entity / get_entity_detail for the boilerplate — cursor paging, filters, and error mapping already live there.

Register it in the app factory

Add app.include_router(<resource>.router, prefix="/v1") in main.py, inside the enable_data_routes block.

Define request/response schemas

Add Pydantic models to schemas.py. Scope decision #5 leans toward extra="forbid" on write bodies so the web app gets clear errors, not silent drops.

Map QBO's quirks

Check how the entity behaves in QBO: hard-delete vs. deactivate, per-line vs. read-modify-write, which fault codes it can raise. Extend the fault → HTTP mapping in _common only if the entity introduces a new one.

Test at the transport layer

Add an integration suite under tests/integration/ using MockTransport and the _Recorder pattern — assert on the QBO request the client emits, not on live QBO.

If it's a bigger shape

A feature that isn't a plain CRUD resource (e.g. reports, webhooks, a second realm) crosses the scope contract. Those are called out as non-goals / open questions in the scope doc — worth a design note before building, since they touch auth, caching, or statelessness assumptions.

08 What to watch for

Landmines and load-bearing conventions worth knowing before you touch anything.

rotation

Any code path that calls Intuit's token endpoint must persist the rotated refresh token, and do it under refresh_lock. This is the single most breakable invariant in the service.

sync only

QBClient is deliberately synchronous — sync route handlers run in FastAPI's threadpool. Don't introduce async def handlers that call it directly, or you'll block the event loop.

boot guard

create_app() refuses to boot if /admin/* is enabled on Cloud Run (K_SERVICE set) with neither an allowlist nor a launch secret. New admin routes inherit this gate.

two pagers

There are two paging mechanisms: api/pagination.py (paginate() generator) and the route-layer cursor paging in _common.list_entity (fetch limit+1, opaque cursors). List routes use the latter — follow it for consistency.

envelope

Every response — success and error, including ASGI-level 403/500 — shares one envelope carrying request_id and intuit_tid. Keep new routes on the shared helpers so they stay in the envelope.
